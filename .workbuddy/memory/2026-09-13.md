## 小问助手 · 桌面 AI 快捷问答工具（从零开发完成）

**需求**：电脑右下角常驻一个 AI 小助手，随时可问、可快捷键语音问答。
**确认的技术选型**（用户选择）：在线大模型 API + 系统语音识别/朗读 + Electron 桌面应用。

**成果**：
- 完整 Electron 32 项目，原生 JS + Vite 5，无前端框架依赖。
- 打包产物：`dist-app/小问助手 Setup 1.0.0.exe`（80 MB，NSIS 安装包，可选安装目录）。
- 免安装版：`dist-app/win-unpacked/小问助手.exe`。

**核心文件**：
- `src/main/main.js` — 主进程：悬浮球窗口、面板窗口、设置窗口、托盘、全局快捷键、config.json 读写（自实现，未用 electron-store）。
- `src/main/preload.js` — contextBridge 暴露 `window.xw` API（21 个方法）。
- `src/renderer/ball.html` + `js/ball.js` — 悬浮球：单击开面板、双击语音、拖动+边缘吸附、右键菜单。因 transparent 窗口下 `-webkit-app-region: drag` 会吞掉点击事件，改为手动 mouse 事件 + IPC 移动窗口。
- `src/renderer/panel.html` + `js/panel.js` — 一个 HTML 双用途：`#settings` hash 区分对话页/设置页。三个窗口共用同一文件。
- `src/renderer/js/api.js` — OpenAI 兼容接口的 SSE 流式调用 + 测试连接。
- `src/renderer/js/speech.js` — Web Speech API 语音识别 + SpeechSynthesis 朗读（离线）。
- `src/renderer/js/markdown.js` — 自写轻量 Markdown 渲染器（先转义再套语法，代码块用占位符保护）。

**关键坑与解法**：
1. **Electron 打包失败 - winCodeSign 解压符号链接报错**：沙箱无权限创建 macOS 的 .dylib 符号链接。解法：`win.signAndEditExecutable: false`，并设 `CSC_IDENTITY_AUTO_DISCOVERY=false`。
2. **app.asar 被占用无法覆盖**：残留 Electron 进程锁住输出目录。解法：每次换新的 `directories.output`（release → release-out → dist-app）。
3. **bash 工具在此环境不可用**：coreutils 缺失（ls/cat/tail 全无）。**此后一律用 Python 执行 shell 命令并捕获输出**，PowerShell 工具本环境也不返回 stdout。
4. **测试启动要清 `ELECTRON_RUN_AS_NODE`**：否则 electron.exe 以纯 Node 模式运行，报 `app.getPath undefined`。GPU 在沙箱不可用，需加 `--disable-gpu --use-angle=swiftshader`。
5. **agent-browser 截图语法**：`screenshot [path]`（路径是位置参数，不是 `--out`）。

**验证方式**：用 `--remote-debugging-port` + 自写极简 WebSocket CDP 客户端，直接 eval 生产构建的页面，确认 IPC 桥接完整、5 个设置分区、6 个服务商选项、面板/悬浮球 DOM 均正常。

**遗留**：`build/dist-nsis.log`、`build/vite2.log` 两个日志文件被沙箱 trash 机制锁住删不掉，无害（不参与打包）。

## 修复：双击打不开（v1.0.0 → v1.0.1）

**用户反馈**：「打不开呢？」

**根因**：GPU 进程启动失败导致进程直接退出，界面来不及显示就没了。
```
FATAL:gpu_data_manager_impl_private.cc(436)] GPU process isn't usable. Goodbye.
```
实测发现：`--disable-gpu` 单独用**不够**，Chromium 仍会尝试拉起 GPU 子进程；
只有加上 **`--no-sandbox`** 才能真正启动。触发场景：虚拟机、远程桌面、
驱动异常的机器、企业安全软件、受限账户。

**排查方法**（可复用）：
1. 直接 subprocess 启动 exe，捕获 stdout/stderr，看 `FATAL` 行。
2. 遍历参数组合逐个测存活：`--disable-gpu` / `+--no-sandbox` /
   `+--disable-gpu-compositing` / `+--use-angle=swiftshader` /
   `--in-process-gpu`，用 `p.poll() is None` 判断是否存活。
3. 结论用表格对照，一眼看出哪个参数是关键。

**v1.0.1 修复方案**（`src/main/main.js` 顶部，必须在 app ready 前）：
- **Windows 默认走软件渲染** + **统一关闭进程沙箱**（`no-sandbox`），
  优先保证「能打开」。界面元素少，软件渲染开销可忽略。
- 三级决策顺序：用户开关 > 上次崩溃标记 > 命令行/默认值。
- 崩溃自愈：`.booting` 标记（启动时写、ready 后删）+ `.crash-count` 计数；
  连续失败累加，`crashCount >= 2` 追加 no-sandbox。
- `child-process-gone` 监听 GPU 子进程异常，落盘 `.gpu-off` 标记。
- 设置页新增「显示与兼容性」区块：GPU 状态显示 + 手动开关 + 重启按钮。
- 新增 IPC：`gpu:status` / `gpu:set-disabled` / `gpu:restart`。
- 留了逃生门：`--enable-gpu` 或 `XIAOWEN_DISABLE_GPU=0` 强制硬件加速。

**重要环境教训**：
- `app.getPath('userData')` 在模块**顶层**调用可能抛错或返回错误路径。
  实测 `electron <script>` 返回 `Roaming\Electron`，
  `electron .`（有 package.json）才返回 `Roaming\xiaowen-assistant`。
  所以标志文件路径**不能只依赖它**，要有 APPDATA 手工兜底。
- **本沙箱会静默拦截文件写入**：日志显示「已写入启动标记」，
  但文件实际不存在。因此自愈闭环在沙箱内**无法完整验证**，
  只能验证分支逻辑正确 + 无参数启动成功。真实用户环境不受此限。

**验证结果**：零参数启动（模拟双击）→ `ALIVE=True`，日志
`[gpu] 软件渲染` + `[sandbox] 已关闭进程沙箱`。打包产物
`release-v1.0.1/小问助手 Setup 1.0.1.exe`（80 MB）。

**遗留**：旧构建目录 `dist-app`、`release`、`release-final`、`release-out`
被沙箱 trash 机制锁住未能删除，无害（不影响新构建）。

## 修复：设置页打不开 + 启动被残留锁拦住（v1.0.1 → v1.0.2）

**用户反馈**：「设置页面 打开还是 首页。」

### 两个独立问题，都定位并修复

**问题 A（渲染层）：hash 路由没真正切 DOM**
- `loadFile(path, {hash:'settings'})` 在 `file://` 协议下不可靠；
  更关键的是 `panel.js` 的 `init()` 即使识别到设置页，**也没有切换 DOM** ——
  `#app` 没隐藏、`#settings` 没显示。
- 修复：`panel.js` 改为显式 `showView('settings'|'chat')` 切换 display；
  `main.js` 加 `page:mode` IPC（页面 ready 后主进程主动告知角色）作为双保险；
  `initSettings()` 加幂等守卫，避免重复绑定。
- 验证：`hash=#settings` / `app=none` / `set=flex` / 6 个分区 / 6 个服务商。

**问题 B（根本原因）：残留的单实例锁让新进程静默退出**
- 现象：双击 exe 后进程**瞬间退出，exit code 0，无任何报错**。
- 根因：`%APPDATA%\xiaowen-assistant` 里残留了 Chromium 的 `lockfile`
  （上次进程被强杀留下），`app.requestSingleInstanceLock()` 因此返回 false，
  代码走 `app.quit()` 静默退出。用户看到的「打不开」「设置还是首页」
  其实是**旧实例还活着但窗口不可见**。
- **决定性证据**：`--user-data-dir=<干净目录>` 启动 → 一切正常；
  改回默认目录 → 必然失败。

### 排查方法论（重要，可复用）
1. 写 `launch.log` 诊断日志（`~/.xiaowen/launch.log`），记录
   `ready` / `lock` / `quit` / `watchdog` / `child-process-gone` 等事件。
   **日志不要放 userData** —— Chromium 会扫描该目录并清理非它自己的文件。
2. 用 PowerShell 查 `Singleton*` / `lockfile` 是否存在，以及
   `Get-Process | Where ProcessName -match '小问|electron'` 找残留进程。
   **本次关键突破就在这一步：发现 6 个残留 `小问助手.exe` 进程。**
3. `taskkill /F /IM 小问助手.exe /T` 清掉残留后再测，问题立刻消失。

### v1.0.2 修复内容（`src/main/main.js`）
- **启动前清残留锁**：`clearStaleSingletonLocks()` 解析锁文件里的 PID，
  仅在「解析不出 PID 或该进程已死」时清理 `SingletonLock/Cookie/Socket/lockfile`。
- **二次确认而非盲信锁**：`requestSingleInstanceLock()` 失败时，
  用 `probeRunningInstance()`（tasklist 查 `小问助手.exe`）做独立信号确认；
  确认无实例 → 清锁重试；确认有实例 → 正常退出。避免误判导致「双击没反应」。
- **看门狗**：启动 6 秒后自检悬浮球窗口是否存在且可见，异常则重建/强制显示。
- **second-instance 加固**：再次双击时确保悬浮球可见 + 打开面板。
- 集中到 `startApp()` / `bootstrapApp()` 两个函数，替换原先内联的锁逻辑。

**验证结果**（打包版零参数启动）：
```
[ready] 初始化成功
```
零参数启动存活；点设置 → `hash=#settings`、`app=none`、`set=flex`；
对话面板独立窗口 `app=flex`、`set=none`；重复点设置窗口数仍为 1。

**打包产物**：`release-v1.0.2/小问助手 Setup 1.0.2.exe`

**环境教训补充**：
- 打包后的 exe **不接受** `--remote-debugging-port`（`bad option`）——
  该参数必须先于 app 初始化，需在 `main.js` 里读 argv 后

## 修复：HTTP 401 Incorrect API key（v1.0.2 → v1.0.3）

**用户反馈**：对话一直返回 `⚠️ 请求失败：HTTP 401 · Incorrect API key provided.`

### 根因：渲染进程拿到的是打码后的 Key

`main.js` 的 `sanitizeConfig()` 把真实 Key 替换成 `'__KEEP__'` 占位符，
并把打码值放在 `apiKeyMasked`（形如 `sk-abc***wxyz`），目的是「Key 不出主进程」。

但 `panel.js` 的调用处写错了：

```js
// 旧代码（错误）
apiKey: cfg.apiKey === '__KEEP__' ? cfg.apiKeyMasked : cfg.apiKey
```

`cfg.apiKey` 恒等于 `'__KEEP__'`，所以取到的永远是 **带 `***` 的打码串** ——
`***` 是 UI 显示用的修饰符，服务端当然判为无效 Key → 401。

同类问题还有两处：
- 设置页「测试连接」：不改 Key 直接点 → 拿 `'__KEEP__'` 去请求。
- 设置页填充表单时把打码值写进 input，用户点保存 → 把 `xxx***xxx`
  当成真 Key 存进 config.json（**会永久损坏配置**）。

### 修复方案（架构调整）

**把大模型请求整体挪到主进程**，渲染进程只传消息内容，真实 Key 永不进入页面上下文：

- 新增 IPC：`chat:stream`（SSE 逐行解析 + `chat:delta` 事件回推）、
  `chat:test`、`chat:abort`。
- `preload.js` 暴露 `chatStream` / `chatTest` / `chatAbort` / `onChatDelta`。
- `api.js` 重写为薄封装，只负责订阅分片与转发调用，不再直接 fetch。
- `panel.js` 权限判断改为只看 `cfg.apiKeyMasked` 是否存在（渲染进程无需真 Key）。
- 输入框不再回填打码值，改为 `placeholder` 提示「已配置：xx***xx（留空保持不变）」；
  留空 = 沿用旧 Key，填了才覆盖。
- **双层防御**：`chat:test` 与 `config:set` 都检查 `includes('***')`，
  发现打码串直接回退到已保存的真实 Key（并提示用户重新粘贴）。
- 顺带修好「停止」按钮：原来只改本地 flag，主进程仍在消费 token；
  现在 `stopStreaming()` 会调 `chat:abort()` 真正中断请求，且保留已收到的内容。

### 验证方法（值得复用）

起一个**本地 mock OpenAI 服务**（Python `http.server`，监听 127.0.0.1），
让它校验 Authorization 并**记录收到的 header**。这样能把「Key 到底发出去了什么」
变成可直接断言的事实，而不是靠猜。配套验证四点：

1. 正常流式对话 → 成功，分片拼接正确
2. 测试连接（用已保存的真 Key）→ 成功
3. 传入打码 Key → 被拦下并明确报错，**绝不发往网络**
4. 保存打码 Key → config.json 里的真实 Key 不被污染

**铁证输出**（服务端视角）：
```
'Bearer sk-test-1234567890abcdefghijklmnopqrstuvwxyz'  | stream = True
'Bearer sk-test-1234567890abcdefghijklmnopqrstuvwxyz'  | stream = False
```
完整 Key、无 `***`、长度一致 —— 源码版与打包版均通过。

**打包产物**：`release-v1.0.3/小问助手 Setup 1.0.3.exe`

### 教训

「脱敏」这类安全机制会**悄悄改变数据语义**，凡是跨进程传递被脱敏字段的地方
都要单独审视。本次是同一个字段在三处被误用（对话、测试连接、保存）。
更稳的做法：**让脱敏字段只用于显示，绝不参与任何业务逻辑**；
需要真值时一律回主进程取。
